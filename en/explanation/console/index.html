    Flight console¶

    The console (python -m console.server) is the layer that stitches the browser page, the autopilot in src/, and FlightGear together. It runs on the local machine only, follows the same pattern as arena/ (stdlib ThreadingHTTPServer, bind to 127.0.0.1, per-run token), and reuses fly.run() — there is no parallel flight loop.

    Processes and ports¶

    flowchart LR
  BR["Browser<br/>(http://127.0.0.1:8770)"] <--> SRV["console.server<br/>(HTTP + SSE)"]
  SRV -- "spawn" --> RUN["console.runner<br/>(imports src/fly*.py)"]
  SRV -- "spawn" --> FG["FlightGear<br/>(scripts/launch_flightgear.sh)"]
  FG -- "UDP 5501 · 60 Hz" --> RUN
  RUN -- "UDP 5502 · 10 Hz" --> FG
  RUN -- "UDP 5503 · tick + begin/finished" --> SRV
  SRV -- "SSE: /api/stream" --> BR
    • HTTP 8770 serves the page and the JSON endpoints. It is also the SSE channel that pushes telemetry to the browser.
    • UDP 5501/5502 is the original fly.py pair — nothing changes on the simulator side.
    • UDP 5503 is new: the runner mirrors every (features, cmd) here so the server can fan it out over SSE.

    What the server does¶

    • Serves index.html, CSS, JS, PNG as static (MIME whitelist).
    • Exposes /api/models, /api/status, /api/piloto (GET) and /api/fly/start, /api/fly/stop (POST with X-Console-Token).
    • Keeps a single flight session (Session): FLY fails if a flight is already running — same rule as scripts/run_flight.sh.
    • _launch_fg_after_delay sleeps 3 s before calling the launcher — time for the runner to bind UDP 5501, exactly like run_flight.sh already does.
    • STOP sends SIGTERM to the runner only. The handler in fly.py turns that into KeyboardInterrupt, so the finally block saves the log. FlightGear stays open and the user closes it by hand, as per convention.

    What the runner does¶

    console.runner is a short-lived subprocess:

    1. Imports the src/ module for the chosen model (fly, fly_2, fly_4, fly_8, fly_rnn, fly_pid).
    2. Instantiates the pilot class (e.g. RNNAutopilot("gru_a"), PIDAutopilot()).
    3. Wraps the pilot in a _Spy that, on every on_packet, calls the original and republishes each (features, cmd) over UDP 5503 — without altering the values.
    4. Delegates the loop to fly.run(pilot, name, config). All filter/ZOH/phase/touchdown logic stays there.

    This guarantees that flying from the console produces the same CSV as scripts/run_flight.sh for the same model and scenario.

    What the browser does¶

    • main.js boots: fetches /api/models, /api/status, /api/piloto; subscribes to /api/stream; renders the model cards.
    • instruments/*.js: each canvas is a module (ADI, HSI, IAS/ALT tapes, VSI, yoke, top-down map). All read --fg/--muted/--line from the theme on every frame, so switching themes repaints without a reload.
    • theme.js: dropdown (default AKAER wine on white) + star to pin as principal. Persisted in localStorage under console.theme.principal.

    Pilot flight tracks on the map¶

    console/piloto.py reads the 15 CSVs under Data/csv/voos-piloto/, projects (lat, lon) into the runway frame (along_track_m, cross_track_error_m) using the same constants as src/fly.py, and uniformly downsamples to ~500 points per flight. The result is written to console/cache/piloto_tracks.json (~180 KB total). Invalidated by (name, mtime, size) of the CSVs — any new or changed CSV triggers an automatic rebuild.

    Manual flight and .fgtape¶

    For manual flights (MANUAL=1 on the launcher), console.manual_recorder writes the CSV the same way autonomous flights do (33 columns in artifacts/flights/manual_<scenario>_<timestamp>.csv). In parallel, the launcher sets /sim/replay/record-continuous=1 on FG, which writes the native binary recording to $FG_HOME/Export/. When the user closes FG, a daemon thread in console.server (raw_recording.watch_and_import) moves the newest .fgtape to Data/raw/manual_<scenario>_<timestamp>.fgtape, matching the convention of the 15 original pilot .fgtape files. The CSV covers what we actually use for training today; the .fgtape keeps the 245 raw FG fields around for future analysis.

    Scenarios and FG propagation¶

    console/scenario.py defines the Scenario (wind, environment, initial condition) and scenario_to_fg_args(), which turns a preset into FG flags. The launcher (scripts/launch_flightgear.sh) accepts every field via env var (LAT, LON, HEADING, ALT_FT, SPEED_KT, TIME_OF_DAY, GUST_KT, VISIBILITY_M), falling back to positional defaults. End result: every field editable in the console actually reaches the simulator — gust, visibility, time of day, and initial condition are no longer silently dropped.

    Test battery¶

    The battery mode (console/battery.py) runs N models × M scenarios × R repetitions in interleaved order (one flight per combination before repeating), with a full FG restart between flights (stop_flightgear_hard → wait_flightgear_dead → new spawn). Mutually exclusive with the single flight: /api/fly/start returns 409 if a battery is in progress, and vice-versa.

    Each flight writes a CSV in the usual place (artifacts/flights/) with the same schema as a single flight; the BatteryRunner writes artifacts/baterias/<name>/estado.json after each flight with the plan, the outcomes[] (final state, duration, CSV path) and the battery status. SSE events battery.{started,progress,flight_done,finished,error} feed the live panel. The post-battery visual report is scoped in console/NOTAS_V2_FUTURO.md §4.

    The alternative of repositioning the aircraft via telnet 5401 (without restarting FG) is tracked as future work in console/NOTAS_V2_FUTURO.md §1 — worth doing if the restart cost becomes a real battery bottleneck.

    Model page¶

    The ⓘ button on the top-right corner of each card opens view-model, a "from the weights" read of the chosen model. /api/model/<id> (in console/model_info.py) loads the .pt with torch.load(..., weights_only=False) and returns, per sub-network: name, kind (mlp, cascade, gru, pid), layer list (units + activation), input columns grouped by lag/prefix, output, parameter count, best_epoch, validation_flights, learning curve CSV path, and the curve itself. The frontend (console/web/js/model_page.js) renders the diagram as SVG from that structure and plots the curve on a canvas; --fg/--line are read on every repaint, so switching themes needs no reload. The training date comes from, in order: a training.json next to the weights (if any), or the .pt file mtime; the footer shows which source was used.

    PID is a special case: PID_LOOPS in console/model_info.py hardcodes the 10 cascade blocks (lateral approach, flare, longitudinal, speed), and the UI shows "classical controller — not trained" instead of a curve. GRU uses h0 as a learned nn.Parameter; the diagram shows gru.weight_ih_l0 → head.weight.

    Model comparison¶

    The comparison view (COMPARAR MODELOS button → view-compare, implemented in console/web/js/compare.js) stacks panels vertically, with no limit — each panel plots the mean (log) of train and validation MSE over that model's sub-networks. Panel state is stored in the URL hash (#comparar=mlp_5,mlp_8,gru_a), so the link is shareable and survives a reload. MESMA ESCALA toggles a global Y axis shared across all panels — useful to compare magnitude; without it, each panel uses its own range.

    The per-epoch average is partial: at each position, only the components whose curve still has data there enter the mean (sub-networks with short early stopping drop out earlier). The COPIAR LINK button copies location.href to the clipboard.

    Security (localhost-only)¶

    Same as arena/:

    • Binds to 127.0.0.1 only (never listens on the network).
    • Host whitelist: 127.0.0.1:8770 or localhost:8770.
    • Origin whitelist on POST (only when the origin is set).
    • Fresh random token per run, required on every POST via X-Console-Token.

    No token persistence across runs and no user auth — assumes a single-operator machine.

    Differences from scripts/run_flight.sh¶

    run_flight.sh Console
    Model selection CONTROLLER=nn/pid + manual edits card dropdown
    Wind scenario positional args header fields
    Visualisation FlightGear only ADI/HSI/tapes/map + FG
    How to stop Ctrl+C in the terminal STOP button (SIGTERM)
    Flight log artifacts/flights/*.csv identical

    The console does not replace the shell — it is a more comfortable layer over the same fly.run().
